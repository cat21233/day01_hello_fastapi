## 二、概念预习（理解"为什么"，明天才写得出来）

### 概念 1：pytest —— 为什么必须学测试

**你现在的验证方式**：手动开 `/docs`、点 Execute、肉眼看返回。这有个致命问题——**你改一次代码，就要把所有接口重新手测一遍**，漏测一个就可能在不知不觉中把功能改坏。

**测试解决什么**：把"手动点"变成"自动跑"。写一次测试代码，以后每次改完代码跑一条命令，**10 个接口 1 秒全验完**。改坏了？测试立刻报红，指出哪坏了。

**怎么测 FastAPI 接口**（FastAPI 官方方案：TestClient + pytest）：

```python
from fastapi.testclient import TestClient
from main import app

client = TestClient(app)

def test_read_root():
    resp = client.get("/")
    assert resp.status_code == 200
    assert resp.json() == {"message": "Hello World"}
```

- `TestClient(app)`：一个"假的浏览器"，直接对 app 发请求，**不用真的启动服务**（基于 httpx，你 D5 学过的）
- `assert`：Python 断言，条件不成立就报错
- pytest 会**自动发现**文件名 `test_*.py` 里、函数名 `test_*` 的函数并执行

**关键认知**：测试不是"写代码之后的事"，是**写代码的验收标准**——"这个接口算不算写完？测试通过才算"。

### 概念 2：Git feature 分支 —— 团队协作的规矩

**你现在的工作方式**：所有提交都直接堆在 `main` 分支上。真实项目里这是**禁忌**——`main` 应该永远是可发布的稳定版本。

**分支解决什么**：开发新功能时**开一条新分支**（比如 `feature/pytest`），在上面随便改随便提交，改好了再**合并回 main**。这样 main 永远干净，队友之间互不干扰。

```bash
git checkout -b feature/pytest   # 创建并切换新分支
# ... 在分支上写测试、提交 ...
git checkout main                # 切回 main
git merge feature/pytest         # 合并分支
```

**关键认知**：`main` = 稳定的"发布版"；分支 = 你的"工作台"。工作台弄乱了，不影响发布版。

### 概念 3：README —— 项目的"门面"

面试官/陌生人打开你 GitHub 仓库，**第一个看的就是 README**。它要回答三个问题：
1. **这是什么项目？**（一句话 + 技术栈）
2. **怎么跑起来？**（启动命令，别人照着能做）
3. **有哪些接口？**（接口清单 + 示例）

典型结构：项目名 → 简介 → 技术栈 → 目录结构 → 启动方式 → 接口示例 → （博客/联系方式）

## 四、环境坑提醒（避免重踩）

- **测试跑法**：`uv pip install pytest`（uv 的 venv 没 pip，用 uv pip）
- **TestClient 不需要启动服务**——别再 `uvicorn main:app` 跑着测，`pytest` 直接跑
- **测试文件放项目根目录**：`test_main.py`（pytest 默认找根目录）
- **GitHub push 需开 VPN**（老规矩）
- **沙箱 `--reload` 不生效**（老规矩，但测试不用它）
